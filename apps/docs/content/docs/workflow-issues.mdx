In Si-Multica, a **skill** is capability, an **issue** is the goal, a **Workflow** is how complex AI work should run, and a **Run** is the visible execution record.

This page has two paths:

- If you operate agents day to day, start with the lifecycle and glossary.
- If you maintain Si-Multica or agent-runtime, read the control boundaries and implementation map.

## The short version

When a task is too complex or risky to hand to an agent as a black box, use a Workflow. The agent drafts how the work should run. A human inspects and edits the Draft, then sets it as the Active Workflow. Each Run follows the Active Workflow snapshot, reports Step progress through `workflow_run`, and pauses at Review Steps until a human approves or rejects.

<Callout type="info">
Skills are not runs. A skill is reusable knowledge and workflow structure that an agent may use when drafting a Workflow for a specific goal.
</Callout>

The important ownership split is:

- **Agent drafts** how the complex work should run.
- **Human inspects** the Draft and sets it as the Active Workflow.
- **Backend validates** the Active Workflow and owns product side effects.
- **Sidecar executes** the backend-validated snapshot.
- **`workflow_run` records** what users see in the UI.
- **Workflow paths decide** what happens after each Step, including Review Step approval or rejection.

## The mental model

Think of the system as a chain from reusable capability to a concrete run:

| Thing | What it answers | Who mainly uses it |
|---|---|---|
| Skill | What can this agent know or do repeatedly? | Agent authors and main agents |
| Skill workflow | What reusable subgraph can this skill offer? | Main agents and skill editors |
| Main issue | What does the user want done? | Users and operators |
| Workflow Draft | How does the agent propose this work should run? | Agents and humans |
| Active Workflow | What plan is approved for new runs? | Users, backend, sidecar |
| Step | What is one observable stage in the run? | Sidecar and workflow UI |
| Review Step | Where must a human approve or reject? | Users and operators |
| Dispatch | What carrier executes this step? | Backend validation and sidecar |
| Sub-issue | What work item was created for a sub-agent? | Operators and sub-agents |
| Run / `workflow_run` | What happened during this execution? | UI, operators, developers |

## Glossary

### Main issue

The main issue is the user's goal container. It holds the original request, the visible workflow progress, and the final agent summary.

### Main agent

The main agent is the planner, orchestrator, and final owner. It reads the main issue and its own attached skills, then submits a runtime workflow. It should not bypass the backend to create workflow-managed sub-issues directly.

### Skill

A skill is a reusable knowledge pack. It may contain instructions, examples, tools guidance, reference files, and workflow shapes. A skill is not a single execution.

### Skill workflow

A skill workflow is a reusable workflow shape or subgraph inside a skill. The main agent may reuse it as-is, trim it, combine it with other skill workflows, or modify it for the current issue.

### Workflow

A Workflow is the runbook for complex AI work. The agent creates a Draft, a human inspects it, and the approved plan becomes the Active Workflow used for new Runs.

### Step

A Step is one observable stage in the graph. A Step is not automatically a sub-agent or a sub-issue. Its `type` says what it does; its `dispatch` says how it is carried out.

### Review Step

A Review Step pauses the Run and asks a human for one decision: approve or reject. The decision becomes Step output. The workflow path decides what happens next.

### Run / `workflow_run`

`workflow_run` is the visible execution record. It stores the workflow snapshot, status, current step, step states, outputs, errors, review decisions, and references such as sub-issue ids or task ids.

## Native issue mode vs workflow-managed mode

Si-Multica supports two valid execution models.

### Native issue mode

Native issue mode is the ordinary parent/child issue collaboration model. A child issue completing can wake the parent issue assignee, and the parent assignee decides what to do next.

### Workflow-managed mode

Workflow-managed mode uses `workflow_run` as the controller. A workflow-managed child issue is only the carrier for a `dispatch=subissue` Step. When that child issue completes, the result goes back to the Run so the graph can advance.

<Mermaid chart={`

<Callout type="warning">
A workflow-managed sub-issue should not also trigger the native parent auto-wake path. That would create two controllers: the Run and the parent issue assignee.
</Callout>

## Dispatch and carrier

| Dispatch | Carrier | Creates a Simultica child issue? | What users see |
|---|---|---:|---|
| `subissue` | Child issue + task | Yes | Step status, output, and child issue link |
| `inline` | Sidecar or backend internal execution | No | Step status and internal result |
| `human_gate` | Review Step | No | Approval state and review decision |
| `main_issue_task` | Main issue task for review/final | No | A main-agent step and final summary |
| `direct_subagent` | Reserved for a future direct subagent session | No | Not a current product promise |

Only `dispatch=subissue` creates a sub-issue. Other Steps can still be visible in the workflow graph without creating child issues.

## Review Step decisions

Review Steps are intentionally narrow:

```text
Review Step waits
  -> user approves or rejects
  -> decision is written as step output
  -> workflow path decides next step
```

The review action does not let the user pick an arbitrary next Step or edit the running workflow. If rejection should trigger rework, the Workflow must define that path.

## Where progress lives

For users, progress lives in the Run detail and workflow panel. For developers, the user-visible state lives in `workflow_run`.

The LangGraph checkpoint used by agent-runtime is different: it is internal engine recovery state. Do not use it as the UI fact source.

## Stop and replan

The current Run uses a snapshot. If the plan is wrong, the product model is:

1. Stop or cancel the current run.
2. Preserve its `workflow_run` record for auditability.
3. Replan or edit the Draft, set it active, and create a new Run with a new snapshot.

This keeps the old execution understandable instead of mutating history in place.

## Troubleshooting checklist

For operators:

- Open the Run detail or workflow panel first.
- If a Step created a sub-issue, open that child issue for sub-agent details.
- If a Review Step is waiting, approve or reject it from the Run detail.
- Check whether the run is `running`, `failed`, `cancelled`, or `done`.
- If the runtime is offline, check the Runtimes page and daemon status.

For developers:

- Check `workflow_run.status`, `current_node`, `nodes_state`, and `error`.
- Check backend validation errors from the runtime workflow submit path.
- Check sidecar logs for build, polling, cancellation, or node execution failures.
- Verify whether the failing Step is `subissue`, `inline`, `human_gate`, or `main_issue_task`.
- Keep UI state tied to `workflow_run`, not to LangGraph checkpoints.
