In Multica, a **skill** is capability, an **issue** is the goal, a **runtime workflow** is the plan, and `workflow_run` is the visible execution record.

This page has two paths:

- If you operate agents day to day, start with the lifecycle and glossary.
- If you maintain Multica or agent-runtime, read the control boundaries and implementation map.

## The short version

When an issue is assigned to an agent, the issue is the user's goal container. The main agent owns the plan. It reads the issue context and its attached skills, then submits a runtime workflow draft. The backend validates that draft, creates a `workflow_run`, and starts the agent-runtime sidecar. The sidecar executes the validated workflow snapshot and keeps updating `workflow_run` so the UI has one clear source of truth.

<Callout type="info">
Skills are not runs. A skill is reusable knowledge and workflow structure that an agent may use when planning a run for a specific issue.
</Callout>

The important ownership split is:

- **Main agent plans** the workflow for the issue.
- **Backend validates** the workflow and owns product side effects.
- **Sidecar executes** the backend-validated snapshot.
- **`workflow_run` records** what users see in the UI.

## The mental model

Think of the system as a chain of increasingly concrete artifacts:

| Thing | What it answers | Who mainly uses it |
|---|---|---|
| Skill | What can this agent know or do repeatedly? | Agent authors and main agents |
| Skill workflow | What reusable subgraph can this skill offer? | Main agents and skill editors |
| Main issue | What does the user want done? | Users and operators |
| Runtime workflow | What is the issue-specific execution plan? | Main agents, backend, sidecar |
| Workflow node | What is one step in the plan? | Sidecar and workflow UI |
| Dispatch | What carrier executes this node? | Backend validation and sidecar |
| Sub-issue | What work item was created for a sub-agent? | Operators and sub-agents |
| `workflow_run` | What happened during this execution? | UI, operators, developers |

## Glossary

### Main issue

The main issue is the user's goal container. It holds the original request, the visible workflow progress, and the final agent summary.

### Main agent

The main agent is the planner, orchestrator, and final owner. It reads the main issue and its own attached skills, then submits a runtime workflow. It should not bypass the backend to create workflow-managed sub-issues directly.

### Skill

A skill is a reusable knowledge pack. It may contain instructions, examples, tools guidance, reference files, and workflow templates. A skill is not a single execution.

### Skill workflow

A skill workflow is a reusable template or subgraph inside a skill. The main agent may reuse it as-is, trim it, combine it with other skill workflows, or modify it for the current issue.

### Runtime workflow

A runtime workflow is the final issue-specific execution graph submitted by the main agent and validated by the backend. Once stored in `workflow_run.definition_snapshot`, it is the snapshot that the sidecar executes.

### Workflow node

A workflow node is one step in the graph. A node is not automatically a sub-agent or a sub-issue. The node's `type` says what it does; the node's `dispatch` says how it is carried out.

### `workflow_run`

`workflow_run` is the visible execution record. It stores the workflow snapshot, status, current node, node states, outputs, errors, and references such as sub-issue ids or task ids.

## Native issue mode vs workflow-managed mode

Multica supports two valid execution models.

### Native issue mode

Native issue mode is the ordinary parent/child issue collaboration model. A child issue completing can wake the parent issue assignee, and the parent assignee decides what to do next.

### Workflow-managed mode

Workflow-managed mode uses `workflow_run` as the controller. A workflow-managed child issue is only the carrier for a `dispatch=subissue` node. When that child issue completes, the result goes back to the workflow run so the graph can advance.

<Callout type="warning">
A workflow-managed sub-issue should not also trigger the native parent auto-wake path. That would create two controllers: the workflow run and the parent issue assignee.
</Callout>

## Dispatch and carrier

| Dispatch | Carrier | Creates a Simultica child issue? | What users see |
|---|---|---:|---|
| `subissue` | Child issue + task | Yes | Node status, output, and child issue link |
| `inline` | Sidecar or backend internal execution | No | Node status and internal result |
| `main_issue_task` | Main issue task for review/final | No | A main-agent node and final summary |
| `direct_subagent` | Reserved for a future direct subagent session | No | Not a current product promise |

Only `dispatch=subissue` creates a sub-issue. Other workflow nodes can still be visible in the workflow graph without creating child issues.

## Where progress lives

For users, progress lives in the workflow panel on the main issue. For developers, the user-visible state lives in `workflow_run`.

The LangGraph checkpoint used by agent-runtime is different: it is internal engine recovery state. Do not use it as the UI fact source.

## Stop and replan

The current runtime workflow is a snapshot. If the plan is wrong, the product model is:

1. Stop or cancel the current run.
2. Preserve its `workflow_run` record for auditability.
3. Replan and create a new run with a new snapshot.

This keeps the old execution understandable instead of mutating history in place.

## Troubleshooting checklist

For operators:

- Open the main issue and check the workflow panel first.
- If a node created a sub-issue, open that child issue for sub-agent details.
- Check whether the run is `running`, `failed`, `cancelled`, or `done`.
- If the runtime is offline, check the Runtimes page and daemon status.

For developers:

- Check `workflow_run.status`, `current_node`, `nodes_state`, and `error`.
- Check backend validation errors from the runtime workflow submit path.
- Check sidecar logs for build, polling, cancellation, or node execution failures.
- Verify whether the failing node is `subissue`, `inline`, or `main_issue_task`.
- Keep UI state tied to `workflow_run`, not to LangGraph checkpoints.
